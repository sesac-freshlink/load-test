## 3. 품절이 뜨지 않은 이유

코드 동작:
1. 입장 스케줄러가 2초마다 inventory에서 남은 수량을 받아, `남은 수량 − 살아 있는 입장권 수`만큼 앞사람을 입장시킨다.
2. 순번 조회는 `남은 수량 = 0`이고 살아 있는 입장권도 0일 때만 품절(SOLD_OUT)을 준다.
3. 입장권은 5분짜리다. 입장하고 주문하지 않은(포기한) 사람의 자리는 5분 뒤 다음 사람에게 간다.
4. 결제하지 않은 주문은 10분 뒤 "결제 시간 만료"로 취소되고 재고가 돌아온다. k6 가상 고객은 결제하지 않는다.

order 로그 (KST):

| --- | --- |

| 17:22~17:23 | 남은 2,779명이 15분 대기 한도(`MAX_WAIT_S=900`)로 포기하고 k6 종료 |

- 줄 서기가 느려 첫 10분 안에 100개를 다 채우지 못했고, 그 뒤에는 만료로 재고가 계속 돌아와 남은 수량이 0이 된 적이 없다.
- 1,000명 라운드(11/17)는 6분 15초에 끝나 10분 만료 전에 품절이 났다.
- 초과 판매 확인: order 로그에 "선착순 입장권으로 주문" 131건, 재고 예약 실패 0건이다.
- **확인하지 못한 점:** 첫 입장 97명 중 포기 약 10명을 빼면 주문이 약 87건 있어야 하는데, 남은 수량은 22까지만 내려갔다(약 20개 차이). DB에서 상품 15의 주문 상태별 개수로 확인한다.

품절 장면까지 보려면 셋 중 하나를 한다.
1. 입장한 가상 고객이 시뮬레이터 결제 완료(`POST /ops/orders/{id}/simulated-payment`, dev만)를 부르게 k6를 고친다.
2. 한도를 50처럼 낮춰 10분 안에 다 팔리게 한다.
3. `MAX_WAIT_S`를 10분보다 짧게 해서 만료 전에 라운드를 끝낸다.

### 4-1. 11/17 OOM 원인 다시 보기

| 항목 (MB) | 11/17 (Prometheus 추정) | 11/19 (NMT 실측) |
| --- | ---: | ---: |
| working set | 750 | 761 |
| 힙 | 297 | 354 |
| 힙 밖 합계 | 약 452 | 약 407 |

- 힙 밖 메모리는 400~450MB의 고정 바닥이다. 부하가 없을 때(기준점)도 이미 329MB(477 − 148)였다. 클래스 약 31,700개를 띄운 Spring 앱이라 Metaspace·Code·Symbol만 약 300MB다. 새는 메모리가 아니다.
- 부하로 늘어난 것은 힙이다(148 → 354).
- 그래서 11/17 메모의 "힙은 원인이 아니고 네이티브가 늘어 터졌다"는 정확하지 않다. 정확히는 **부하 때 필요한 힙 약 350MB + 고정 힙 밖 400~450MB = 750~800MB가 768MiB를 넘었다.** 오늘 숫자(761)로도 768MiB였다면 남는 것이 7MB뿐이었다.
- 1Gi + 힙 400 고정으로 약 260MB 여유가 생겼다.

### order 2개·gateway 2개·t3.large 2대일 때 산술 추정 (실측 아님)

전제:
- 오늘 실측: 사용자 1명당 약 0.32건/s(설계값은 0.4건/s), order는 요청 1건/s당 CPU 약 1.2m.
- gateway는 재지 않았다. 요청 1건당 order의 절반 정도로 가정했다. **이 테스트는 gateway를 거치지 않는다**(k6가 클러스터 안에서 order를 직접 부른다).
- 노드 1대가 쓸 수 있는 CPU 1,930m. 관측성·ArgoCD 등 평소 사용량 약 0.6코어를 더했다.

### 5,000명 대책 (효과 큰 순)

1. **순번별 폴링 간격**: 앞 순번은 2.5초, 뒤 순번은 10~30초로 묻게 한다. 요청 수 자체가 크게 줄어 효과가 가장 크고 비용이 들지 않는다.
2. 노드 3대 + order 3개 + gateway 3개.
3. 더 큰 노드(예: t3.xlarge).

### order를 2개로 늘리는 순서

1. order-service 매출·픽업 스캔 SSE에 Redis Pub/Sub을 붙인다(코드 작업, 김경우). Valkey는 대기열 때문에 이미 있다.
2. 공용 차트에 podAntiAffinity 또는 topologySpread를 넣어 같은 서비스 파드가 한 노드에 몰리지 않게 한다. 11/19 끝난 뒤 노드 하나(ip-10-0-24-144)에 CPU 요청 97%, 메모리 사용 90%가 몰려 있었다.
3. gitops에서 order `replicaCount`를 2로 올리고(dev 먼저) 3,000명을 다시 돌려 파드당 CPU를 잰다. 그 값으로 5,000명 추정을 고친다.
